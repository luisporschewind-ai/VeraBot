# 长回复折叠（Long Reply Collapse）

状态：iOS 已实现；2026-10-15 按手机排版高度重定阈值（`fix/long-reply-collapse-threshold`）。未构建、未跑 `swift test`、未在模拟器验收。`frontend/web` 冻结，不改。  
范围：仅私聊 `MessageRow` 的 Bot 回复气泡与其上方的工具 trace 卡片；群聊、用户消息不变。

## 问题

很长的 Bot 回复每次进入视口都要整段解析 Markdown（块解析 + `AttributedString(markdown:)` + `NSDataDetector`）并排版大量 `Text`，私聊页滚动卡顿；一两屏长的回复也打断阅读。

## 行为

- Bot 回复超过阈值时默认收起：气泡里只显示截断后的预览，底部约 44pt 渐隐，下面一个小的「展开 ⌄ / 收起 ⌃」按钮（品牌色、footnote）。
- **收起时不渲染全文 Markdown**：`MessageContentView` 只拿到预览字符串，解析与排版成本只与预览长度有关。这是性能要点。
- 展开后渲染全文；展开状态按消息记在 `ChatViewModel.expandedReplies`（键同对话行 id：`m<messageID>`，无 messageID 时用本地 UUID），对话页存活期间保留，滚出视口、历史重载后仍保持；离开对话页后重置为收起。
- 不折叠：用户消息、仍在流式输出的回复（`item.streaming`）。流式结束后若超阈值即收起。
- 朗读、复制、复制链接、删除、👍👎 均作用于全文，不受折叠影响。

## 长度估算

阈值按「在手机上排出来有多高」定，而不是原文字数或 `\n` 行数：带标题、表格、列表的中文回复，几百字就有一两屏。

- **宽度**按半宽单位计：ASCII 占 1；中文、全角标点、emoji 等其他字素占 2。气泡正文宽约 267pt（393pt 屏宽减去列表边距、头像 34、间距 8、右侧留白 24、气泡内边距 28），17pt 中文每行约 15 字 = 30 个半宽单位。
- **高度**按半行计（正文一行 = 2），逐行累加：

| 源文本行 | 半行 | 说明 |
|---|---|---|
| 段落 / 列表项 / 引用 | 2 × ⌈宽度 / 30⌉，至少 2 | 按气泡宽度折行 |
| 标题 `#`～`######` | 同上 + 1 | 字号大、上下有块间距 |
| 表格行（以 `\|` 开头） | 2 | 表格横向滚动，不折行 |
| 表格分隔行 `\|---\|` | 1 | 分隔线 |
| ``` 内的代码行 | 2 | 代码横向滚动，不折行 |
| ``` 边框 / 空行 | 1 | 内边距、语言标签、段间距 |

- **加权字数** = 半宽单位 / 2（中文 1、ASCII 0.5），全文所有字素都算（含 Markdown 符号）。

## 阈值（`VeraBotCore.LongReplyCollapse`）

| 常量 | 值 | 理由 |
|---|---|---|
| `collapseRows` | 28 | 6.1 英寸 iPhone（852pt 高）对话可视区约 660pt（减去导航栏约 103、输入栏与 Home 指示条约 90），中文正文一行约 23pt：约 28 行 = 一屏。一屏内看得完的回复不折叠，要滚动才能看完的折叠 |
| `collapseCharacters` | 500（加权） | 纯段落约 420 字就先触发行数阈值；这条主要兜住不折行的宽表格 / 长代码，它们估算行数少但信息量大 |
| `previewCharacters` | 200 | 预览字素上限，主要约束英文与宽表格 |
| `previewRows` | 8 | 约 1/3 屏，足以看到标题与第一段结论；与折叠阈值相差 3.5 倍，「展开」有实质内容 |

超过任一折叠阈值即折叠（严格大于；恰好等于不折叠）。

「思考助手」的真实回复（本地库）：

| 回复 | 字数 / `\n` 行数 | 估算行数 | 旧阈值（1500 字 / 40 行） | 新阈值 |
|---|---|---|---|---|
| 决策建议（标题 + 表格 + 列表） | 594 / 24 | 约 45（约 1.6 屏） | 不折叠 | 折叠 |
| 同上 + 风险提示 | 716 / 30 | 约 57（约 2 屏） | 不折叠 | 折叠 |
| 简短建议 | 329 / 14 | 约 24（不到一屏） | 不折叠 | 不折叠 |

估算行数取自同形状的测试样例（`LongReplyCollapseTests` 中的 `decisionReply` / `decisionReplyWithRisks` / `shortAdviceReply`）。329 字那条估算约 24 行，离阈值还有约 4 行余量；若某条 300 多字的回复段落更长、超过一屏，也会折叠，这是按高度判定的预期结果。

## 截断规则

字数按字素（Swift `Character`）计，中文、emoji（含 ZWJ 家庭、国旗）、组合字符都算 1 个；行按 `\n` / `\r\n` 分。

1. 跳过开头空行，逐行收入，字数（≤ 200）或估算行数（≤ 8）到上限时停在最后一整行（行尾截断，不补「…」）。
2. 整行放不下、且已收内容不足两项上限的一半（例如整段无换行的长文）时，才在行内按字素截断并补「…」；截断后连同「…」不超过剩余行数（中文长段约 119 字 +「…」），不会切开字素。
3. 截断点落在 ``` 代码块内：代码块前有正文则退回到代码块之前；回复以代码块开头时保留已收代码行并补闭合 ```。预览本身始终是完整的 Markdown，不会出现半个代码块。
4. 收尾：去掉末尾空行、末尾标题，以及只有表头（或表头 + 分隔行）、没有数据行的表格；至少保留第一行。

判定和截断都有提前退出，耗时与阈值相关、与全文长度无关：每行至少 1 个半行、每个字素至少 1 个半宽单位，最多扫描约 1000 个字素或 57 行。

## 工具 trace 卡片

回复上方的 trace 卡片（`TraceView`）只显示一句说明，不铺工具结果原文：

- `read_file` 的结果带最多 3 万字文件内容（`text`），之前走默认分支 `JSONValue.text` 把整个结果拼成一段字符串、无行数限制地放进 `Text`，每次进入视口都要排版整段文件。现在标题为「📄 读取文件」，说明由 `ToolTraceSummary.readFile` 生成，例如「已读取「方案.md」第 1–30000 字，共 52000 字，未读完」，不含文件内容。
- 其他未专门处理的工具用 `ToolTraceSummary.fallback`：格式同 `JSONValue.text`，最多 160 字素，超出补「…」，写满即停，不会先拼出整段原文。
- `ask_bot` 协作回答先截到 400 字素再做行内 Markdown 解析（原来只有 `lineLimit(8)`，解析的仍是全文）。
- MCP 工具只显示「已读取外部资料（约 N 字）」；N 由 `MCPTraceText.contentLength` 给出，后端截断过的 trace 取 `trace_truncated.content`（原长度），否则数 `content`。

后端自 schema v33 起在落库与同步时瘦身 trace（`backend/verabot/core/trace_slim.py`）：`read_file` 不带 `text`，只留 `filename` / `offset` / `length` / `next_offset` / `has_more` / `text_chars` / `text_status` 和 `text_omitted`；其他工具结果里超过 2000 字的字符串截到 2000 字并接 `…[truncated]`，原长度记在 `result.trace_truncated`（点分路径 → 字数）。模型在本轮仍拿到完整结果，只有存下来、同步出去的 trace 变小。存量数据由 v33 迁移改写，见 [known-issues](../testing/2026-10-14-known-issues.md)。

## 测试

`LongReplyCollapseTests`（Swift Testing）：

- 真实形状回归：594 字 / 24 行、716 字 / 30 行的标题 + 表格 + 列表回复折叠，预览为标题 + 第一段；329 字 / 14 行的回复不折叠。
- 阈值上下界（恰好 28 行、恰好 500 加权字不折叠）、`\r\n`、列表折行而表格不折行、空行与标题计入高度、中文按 2 倍权重。
- 截断：按行数 / 字数行尾截断、行内截断条件与长度、开头空行、末尾标题与无数据行表格去掉、代码块退回与补闭合、字素（家庭 emoji、组合字符、国旗）不被切开。
- trace：`read_file` 说明不含文件内容；兜底说明有上限，短结果与 `JSONValue.text` 一致；后端瘦身后的 `read_file` trace（无 `text`）照常解码和显示。`MCPTests.slimmedMCPTraceKeepsOriginalContentLength` 覆盖 MCP 原长度。
