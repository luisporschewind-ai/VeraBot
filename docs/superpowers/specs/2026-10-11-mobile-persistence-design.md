# 移动端 SQLite 持久化设计

日期：2026-10-11

状态：方案已确认并实施，2026-10-12 已整合到本地 main。自动验证/构建/安装与未触发的设备验收见 [本轮交付](../../testing/2026-10-12-main-integration.md)。原设计时的基线与交付限制保留为历史记录，本轮用户另行授权提交、合并和更新设备。

## 目标与范围

用户要求移动端数据持久化，断网时仍能看到对话，不能出现已有内容全部消失的页面。用户已选择 SQLite + 独立数据访问层。

第一轮交付覆盖：Bot/群列表、私聊/群聊完整历史同步和离线阅读、文字草稿、发送失败内容及流式回复中断后的恢复。网络失败、关闭 App、系统回收进程和手机重启不清空已保存内容。

历史保存包含消息正文、服务器时间、工具 Trace、附件元数据、消息反馈、群成员身份快照，以及历史卡片最近一次获取到的状态。离线卡片展示已保存状态，确认/执行仍须联网并由后端重新校验。

后续独立阶段：图片/文件字节的长期离线保存、增量变更日志、离线自动发送队列。首轮附件展示本地保存的名称/类型等资料；已存在的头像文件与内存图片机制继续使用，不承诺所有附件离线打开。

尚未下载的数据无法在首次断网时出现。产品须显示同步是否完整，区分“确实没有消息”“历史尚未同步”和“历史只同步了一部分”。

## 当前实现依据

- `ChatViewModel.load()` 直接调用 `VeraBotAPI.messages`；`items` 是页面内存。用户消息与临时回复同样仅追加到内存；`done` 后才获得服务器消息 ID。
- `ChatView` 的 `input` 是页面状态，退出页面/进程后没有恢复入口。
- `GroupChatViewModel` 持有内存 `GroupChatState` 和草稿，已有轮次恢复、请求 UUID 和会话代号检查，须复用。
- `BotListView` 的 Bot/群数组来自网络请求，没有业务数据库。
- 私聊历史默认 100 条，上限 500 条，无历史游标；群聊已有 `before_id` 分页。
- `APITransport` 使用 ephemeral session 且关闭 URLCache，防止令牌和账号数据进入通用 HTTP 缓存；保持现有设计。
- `AppState` 已将令牌放入 Keychain，保存上次用户 ID，并用 generation 防止旧登录请求污染新会话。
- `AttachmentImageStore` 仅有内存缓存，Quick Look 文件是临时文件；头像已有磁盘缓存。
- 当前后端迁移最高为 v20，工作区有并行未提交改动。实施时重新核对迁移版本，不覆盖并行工作，不自动提交、合并、推送或升级实际服务库。

## 架构与职责

数据方向：页面/ViewModel → ConversationRepository → SQLite 存储；Repository 通过现有 API 拉取后端数据，再将结果写入 SQLite。页面先读本地，不用网络结果作为唯一展示来源。

新增 `VeraBotPersistence` SPM 模块，依赖 `VeraBotCore` 与系统 SQLite C API；用一个串行 actor 持有连接。SQLite 访问、事务和迁移集中在该模块，不在页面编写 SQL。`VeraBotNetworking` 保持传输职责；另增数据访问模块 `VeraBotData`，依赖 Persistence/Networking/Core，封装本地读取与远程同步。

组件职责：

| 组件 | 职责 |
| --- | --- |
| `LocalDatabase` | 打开数据库、准备语句、绑定参数、事务、迁移、关闭与文件清理 |
| `ConversationStore` | 会话、消息、草稿、卡片状态及同步进度读写；不发网络请求 |
| `ConversationRepository` | 本地首屏、列表同步、历史分页同步、删除协调、会话隔离 |
| `ConversationSyncCoordinator` | 当前会话优先，依次同步其余会话；合并重复请求，生命周期取消 |
| `AppState` | 持有当前账号 Repository，登录/退出/服务器切换时替换其作用域 |
| 私聊/群聊 ViewModel | 页面状态与现有 SSE reducer；通过 Repository 保存/恢复消息 |

存储和数据访问层使用可传入临时数据库与现有 API 协议的接口，在 macOS `swift test` 中验证，不依赖 UIKit。

## 本地数据库

位置：`Library/Application Support/VeraBot/Accounts/<scope-hash>/conversation.sqlite`。scope 为规范化服务器地址与服务器用户 ID 的组合；hash 不含令牌。不同服务器上相同用户 ID 不共用数据。首轮按地址隔离；地址变更不自动合并旧库，服务器重置复用 ID 时须清除该作用域重新同步。

数据库目录与 SQLite 主文件、WAL/SHM 均设置 iOS 文件保护，排除设备备份。令牌继续在 Keychain，不入业务表。macOS 测试使用普通临时目录。选择 WAL、foreign_keys=ON、busy_timeout，所有 SQL 参数绑定，迁移使用事务；不通过删除整个库自动修复失败迁移。

本地 schema v1：

| 表 | 主键/内容 |
| --- | --- |
| `conversations` | `(kind, remote_id)`；kind 为 private/group；完整会话模型 JSON、排序信息、最近同步时间 |
| `messages` | 稳定 `local_id` UUID；kind/conversation_id、可空 server_id、排序时间/序号、正文、完整消息模型 JSON、local_status、generation |
| `drafts` | `(kind, conversation_id)`；文字、修改时间 |
| `card_states` | `(kind, conversation_id, card_kind, remote_card_id)`；最近一次服务器状态 JSON |
| `sync_state` | `(kind, conversation_id)`；完成版本、当前同步版本、next_before_id、是否完整、同步错误类别 |
| `sync_staging` | 同步任务 ID、会话、服务器消息 ID、JSON；完整对账的临时数据 |
| `list_state` | Bot/群列表是否首次成功同步及 Bot 上限 |

对服务器消息建立 `(kind, conversation_id, server_id)` 唯一索引；本地临时消息没有 server_id。消息依附会话，确认删除会话时级联清理消息/草稿/卡片/同步暂存。

本地 JSON 是业务模型快照，不是 HTTP 响应缓存。解码失败单独报告存储问题，保留原文件；不能把数据库异常表现为“没有对话”。

## 本地读取与页面状态

首次打开列表：读取本地 Bot/群，立即显示；再独立同步两类列表。只有对应列表完整请求成功后，才对账删除本地已不存在会话。一个请求失败不影响另一个列表及已有记录。

打开会话：先读取最近 100 条本地消息及草稿/卡片状态；向上滚动或点“加载更早的消息”从本地分页，每页 100 条。全部历史存于数据库，不要求一次加载进内存。

页面状态区分：

- 有本地历史：正常显示，网络失败时轻量提示“暂时离线，仍可查看历史”。
- 从未成功同步：首次联网显示加载；网络失败显示“历史尚未同步到这台设备”，不显示新会话欢迎语。
- 部分同步：显示已下载历史，提示“部分历史尚未同步”。
- 同步完成且消息为空：才显示欢迎内容/“从一个话题开始”。
- 本地存储不可用：保留当前页面内存并提示“本地保存暂时失败”；不静默声明已保存。

保留现有 Bot 提示组件和友好文案，数据库错误细节写调试信息。同步不先清空页面，不因历史补齐强制跳回底部；稳定 local_id 保持气泡身份，新增消息按现有滚动策略处理。

## 首轮历史同步协议

首轮采用版本校验的分页全量对账，先保证正确性；后续再增加变更日志和增量同步。仅拉“比最大 ID 新的消息”无法发现跨设备删除，不能作为首轮完整对账。

新增专用端点，保持现有历史接口响应兼容：

- `GET /api/bots/{bot_id}/messages/sync`
- `GET /api/groups/{group_id}/messages/sync`

参数：`limit` 默认 100，范围 1…100；`before_id` 可空且大于 0；`expected_revision` 可空且非负。第一页可携带上次完成版本，版本未变则返回 `unchanged=true`；有未完成暂存时携带当前同步版本和游标续传。

响应：`revision`、`messages`（页内从旧到新）、`next_before_id`、`unchanged`。末页 next_before_id=null；零消息也是一个完整结果。中途版本发生变化返回 409 `sync_revision_changed`，客户端舍弃该轮暂存、保留已展示数据，从第一页重试。一次运行最多自动重启 2 次；仍不稳定就保存已有内容，稍后再同步。

后端增加会话同步版本表，按 user_id + kind + conversation_id 隔离。消息增加/修改/删除、影响消息序列化的反馈与附件元数据变化都在同一写事务中推进版本；群消息状态/内容及其响应中的轮次字段变更同样推进版本。迁移补齐已有会话的初始版本。所有写路径，包括级联删除与清空，须通过触发器或统一写入函数覆盖，测试枚举实际路径。删除整个 Bot/群由完整列表对账处理。

单页在一个显式 SQLite 读事务中完成权限校验、版本检查、消息/Trace/反馈/附件读取及 next_before_id 计算，不能分连接混合读取不同版本。完成最后一页后追加一次版本检查；只有最后校验通过，客户端才提交完整对账。

客户端每页将暂存、游标和同步版本在同一事务中保存，可中断续传。页面可及时看到已下载的新消息，但不根据未完成分页删除旧消息。完整对账事务将服务器记录 upsert、清除该会话暂存中不存在的服务器消息、更新完成版本并清理暂存。临时未获服务器 ID 的本地内容不参与服务器删除对账。

同步与发送/删除协调：本机开始发送、确认删除/清空时增加会话 epoch，取消旧同步结果；活跃 SSE 期间暂停该会话完整对账，其他会话可继续。SSE 结束后重新对账。旧 epoch 的响应不得写库或更新页面。

首屏列表完成后优先同步当前会话，再依次补齐其他会话；App 回前台、用户刷新和网络恢复均可触发。网络监测仅作触发提示，实际请求结果为准。进入后台时停止启动新请求并落盘进度，不承诺 App 关闭后持续同步。

## 草稿、发送与中断恢复

草稿按会话保存，输入变化防抖 300ms；离开页面、进入后台或准备发送时立即保存。若服务器拒绝/发送失败，文字继续可编辑；附件选择暂不纳入首轮草稿持久化，发送时已有附件元数据保存到本地消息。

私聊：发送前先事务保存稳定 local_id 的用户消息和临时回复，状态分别为 sending/receiving；数据库写入失败不清空输入。SSE 文本每 500ms 或累积 2KiB 保存一次；done、error、取消、进入后台和离开页面立即保存。done 将 user_message_id/message_id 绑定原 local_id，不新增重复气泡。

本地状态为 sending、receiving、completed、failed、interrupted、unconfirmed。数据库恢复时把遗留 sending/receiving 转成 unconfirmed/interrupted，保留收到的正文与 Trace，不恢复假装仍在生成的动画。

当前私聊只在 done 获得服务器 ID，没有持久请求标识，无法可靠判断“服务器已收到但手机没收到确认”。首轮保留无服务器 ID 的记录，标注“发送结果尚未确认”，与已同步服务器历史分开表示；不按相同文字/时间猜测匹配、不自动重发。用户可核对历史后重新编辑发送或丢弃该本地记录。完整无歧义恢复需后续后端请求幂等协议。

群聊复用已有 client_request_id、turn_id 和 GroupChatReducer，持久化轮次元数据、已知消息 ID 与部分内容。恢复后优先查询已有轮次，替换该轮消息，不发新的请求 UUID。离线只展示已保存状态；不能将本地 interruption 当成服务器已停止。联网恢复的运行中轮次仍用现有核对机制。

首轮离线点发送保留草稿并反馈需要联网，不加入自动发送队列。跨 App 重启不自动执行任何工具或确认操作。

## 删除、退出与账号隔离

删除消息、清空对话、删除 Bot/群仍保留现有确认和服务器成功条件；成功后立即事务删除相应本地数据，不等待再次拉取。404 依照现有“服务器已不存在”的语义处理。请求失败保留本地数据及失败反馈。

清空对话同时清理该会话临时消息、草稿、卡片和同步暂存；默认保留长期记忆的现有服务端行为。跨设备删除在下一次完整对账后生效。

Repository 捕获 server scope、用户 ID、AuthSession generation 和本机会话 epoch。每次异步返回以及写库前校验；退出/换账号/换服务器先停任务并使旧 Repository 失效，再关闭连接/替换作用域，禁止旧响应重新创建已删除库。

普通网络失败或令牌刷新暂时不可用，不清除本地数据，不强制退出。已确认登录失效沿用现有退出规则。主动退出时关闭数据库后删除当前账号目录；换账号只在新账号成功确认后切换作用域。账号身份未知时不能凭全局 UserDefaults 资料打开其他作用域。

## 迁移和交付边界

本机业务库从 schema v1 开始，App 升级不得重置已保存历史。后端迁移编号在实施时核对；使用测试库验证 v20 及已有数据升级。

开发构建与后端隔离测试通过后准备模拟器离线验收。实际后端迁移/重启、真机安装和手动体验另记证据，不把自动化通过当成设备验收。保留所有不属于本功能的现有未提交改动。

## 必须通过的验证

1. 真实 SQLite 文件关闭后重开：Bot/群、消息正文/时间/Trace/附件元数据/反馈、草稿和卡片状态均还原。
2. 服务器与用户作用域隔离；退出/切换后的延迟网络结果不得写入旧库或新库。
3. 本地先返回，远程超时/断网/5xx 后列表和历史保持；未同步和确认空会话呈现不同状态。
4. 私聊与群聊各超过 500 条：完整分页、本地分页、重复页去重、同步中断续传。
5. 分页间新增/修改/删除导致版本变更：旧任务不做删除对账，重启同步后得到一致结果。
6. 同步中进程退出：暂存/游标事务一致；没有完整版本就不能删除未出现在已下载页里的旧消息。
7. 删除/清空后旧响应返回，数据不能复活；跨设备删除在完整同步后本地移除。
8. 私聊 done 绑定稳定 local_id；done 丢失时保留结果未确认内容且不自动重发；群聊恢复不生成新 UUID。
9. 流式生成中取消、后台、重启：保留最后持久化内容，离线不出现持续生成动画。
10. 草稿防抖和生命周期立即保存；失败发送内容可继续编辑；存储失败不能误报成功或抹掉输入。
11. 后端新接口权限、游标边界、版本、空结果及现有历史 API 兼容；现有删除/反馈/附件/群轮次回归。
12. Swift Package 完整回归与 iOS 构建；模拟器飞行模式冷启动、历史翻页、断网返回列表、账号切换及重启验收。

## 设计取舍

SQLite 和独立数据层已确定。首轮选择全量版本对账，是为了在现有物理删除接口下可靠发现删除，代价为历史变化后需要重新分批读取。增量日志后续优化。

首轮保证本地已有数据不因联网失败消失；完整历史下载完成后可离线阅读。附件原始字节与自动补发后续实现，避免把未具备后端请求身份的私聊重发误称为可靠恢复。
