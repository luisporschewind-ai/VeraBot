> 用户确认计划并授权执行；当前P0–P3已在隔离分支实施，自动验证/取舍/未验收项见[交付记录](../../testing/2026-10-13-primary-bot.md)。下方原设计作为依据，不将原“尚未编码”文字当当前进度。

日期：2026-10-13。用户已回复“OK, 开始实施, 实施前检查进度”，确认推荐 B 的明确交办/周期任务首版范围。实施前复核：本地 main 已到 `b81caed` / schema v25，群接力 `a01b2d7` 已合入，但用户真实模型/交互验收仍待完成。具体 [实施计划](../plans/2026-10-13-primary-bot.md)已写成，待用户审阅并确定执行方式；尚未编码主 Bot。本文中新字段、接口和状态不是现有 API。

## 1. 目标与建议范围

用户希望从现有 Bot 中选一个主 Bot，头像右下角带徽章。主 Bot 是日常任务首选，会主动推进、处理卡住的工作，在需要用户帮助时发起确认。

推荐把主 Bot 定义为“账号内日常工作的默认负责人”。身份选择与主动执行是两个独立设置：选择负责人不自动授权持续检查、后台费用、新工具或其他 Bot 的私聊。普通聊天沿用当前行为；用户明确“持续帮我处理”“每周检查”等，才创建或更新持久任务，创建时说明目标、频率、范围和停止条件。

第一版处理明确交办任务与周期任务，支持有限咨询、资料不足追问、只读重试和确认后继续。不根据普通闲聊自动创造并执行新目标。可主动建议下一步，但建议接受前不成为已授权任务。用户本轮确认后按此范围展开具体计划，先采用本机/App内查看，APNs仍另行交付。

成功标准：用户离开页面后后端仍能推进获准的工作；任务进度可回读；卡住时知道原因并提出具体求助；回答/批准后沿原任务继续；停止、换账号、服务重启和迟到结果不重复执行或恢复旧工作。

## 2. 当前底座与缺口

主线已有 scheduled_tasks/runs/attempts、独立调度/Worker、租约/幂等、只读策略、结果投递、记忆、私聊委派和 MCP 确认卡片。因此无需先搭一套全新基础设施，也不需要一项用户任务一个系统 cron。

缺口包括账号级负责人、iOS 任务入口、通用目标/步骤、持久等待用户、确认结果到任务的回接、跨步骤咨询、原因分类与可恢复上下文。现有排程 resume 不能恢复某一次工作的中间步骤；当前定时后台禁止委派/写入，不能仅修改 prompt 宣称支持这些能力。

群 v2 的任务/步骤/澄清/事件、版本防护和后台接力已由 `a01b2d7` 合入 main，当前源码 v25，用户交互仍待验收。可参考其存储/恢复模式，但没有通用跨群/私聊任务组件，不能直接调用群表承载私聊。主 Bot 新迁移从 v26 开始，执行前仍按实际 schema 顺延。

## 3. 三种接入方式

### A. 只做主 Bot 身份与默认入口

增加选择、徽章、默认打开和账号同步。改动小，适合先确定交互，但没有持续推进或解阻塞能力，不能作为完整主 Bot 功能交付。

### B. 身份 + 有限持续任务（推荐）

复用现有排程与结果投递模式，新增业务目标/步骤、等待用户、确认续跑和有限咨询。首期工具权限清晰、任务来源明确，逐项补齐生命周期。有实际日常使用价值，也能控制回归范围。

### C. 全面主动管家

主动检查提醒、接收插件事件、跨系统发现工作、推断目标、广泛使用工具及电脑操作。需要事件源、授权范围、持续预算、推送和常驻部署等更多机制；当前不宜与第一版一起展开。

建议先交付 B。A 是 B 的第一阶段；C 在 B 的真实任务验收后按事件源逐个增加，不把所有 Bot 变成无边界自动执行者。

## 4. 产品规则与 iOS 入口

- 每账号零或一个主 Bot，由用户明确选择；默认不自动新建或选第一位。现有 Bot 均可被选择，保留自己的昵称、人设和工具权限。
- 详情页原生菜单增加“设为主 Bot”；主 Bot 提供“取消主 Bot”。头像组件统一叠加右下角徽章并附无障碍标签，不覆盖照片或十一种形状，不改变头像自身造型。
- 主 Bot 不等于置顶。保留用户已有排序；助理页提供稳定的主 Bot 快捷入口，普通点击其他 Bot 仍进入对应私聊，不重定向。
- 主 Bot 详情或对话更多菜单提供“任务”：进行中、等你处理、已完成；每项显示目标、负责人、最近进度、下一步和停止/继续。首期不改 Tab 结构。
- 更换主 Bot 只改变后续默认接收者；已有任务保留原负责人。用户可显式移交未完成任务，重新核验接收者权限并冻结新版本，不复制整段私聊或提高权限。
- 删除主 Bot 清空账号关联，暂停它负责的任务，提示重新选择或移交，不悄悄指定替代者。已完成历史保留身份快照。
- 身份、主动开关、预算和任务状态以服务端为准；本地按账号/服务器隔离缓存。旧客户端忽略新身份字段，不具备新任务操作能力。

## 5. 与群聊的边界

账号主 Bot 与群内任务负责人是两种身份。主 Bot 不自动加入所有群，不成为群的固定回应者，也不恢复已确认要移除的 default_bot_id 语义。

群内仍按显式点名、回复关系、当前任务/澄清和意图选择成员。主 Bot 若是群成员，按同样规则参与；可以负责某项群任务，但该职责仅属于当前任务。

建议未来共享步骤身份、状态/版本、租约、调用记账和事件投递等小型基础组件。私聊任务、周期任务与群任务分别有上下文构造器和策略；不直接将群表塞进私聊，或让群任务访问主 Bot 的私有记忆。

群 v2 已合入，用户验收继续独立跟踪。第一版不以大规模重构三个执行器为前提，保持已有定时任务 v1 行为，采用独立业务任务路径；先复用模式，稳定后再评估提取组件。

## 6. 建议服务端结构

### 6.1 数据职责

- 账号设置：primary_bot_id、身份设置版本、主动开关与独立主动预算。由服务端校验关联 Bot 属于当前账号。
- 任务：goal、origin、owner_bot_id、state、version、completion_criteria、授权范围和预算；保留创建者、原消息/排程引用。周期定义继续由 scheduled_tasks 管理，某个周期发生生成一个业务执行任务，不重复建设日历算法。
- 步骤：稳定 step_id/action_key、task_version、负责人、输入引用、结果、租约、尝试次数、调用账目和检查点。
- 等待项：结构化缺失信息或待确认 action_id、提问消息、任务版本、有效期、解决状态和求助去重标识。
- 事件/投递：单调游标与唯一事件 ID；先持久结果，再发送消息/收件箱通知。投递失败只重试投递，不重跑模型。

具体表名在正式实施计划中确定。原则是业务任务/步骤单独建模，不直接把所有新状态塞入 scheduled_task_runs 的现有 CHECK 约束，也不借用 memory_jobs。

### 6.2 执行状态

建议任务状态：queued、running、awaiting_user、awaiting_approval、retry_wait、completed、stopped、failed、interrupted。阻塞原因作为结构化 blocker_code 与可恢复信息保存，不只用一个“blocked”混合所有错误。

SSE 只观察持久事件；模型步骤由 Worker 领取。每完成一步保存结果和后续动作。等待用户时释放执行租约，不占用模型调用或 Worker；服务重启后仍能回读问题、版本和已有结果。

新指令推进任务版本并撤销过时步骤；实际执行前、调用后、保存结果及安排下一步都检查版本/租约。显式停止取消运行与排队步骤；迟到回复可保留已知费用，但不能写过时正文或安排后继。

周期到来时若前一轮仍在等用户，首版跳过新一次并记录原因，不叠加相同求助。下一次正常排程保留；回答只恢复原执行，不重新运行之前完成的周期。

## 7. 处理阻塞与确认续跑

- **服务临时失败**：对确定可重试的只读请求使用现有 30/120 秒、最多三次规则；超过上限后保存失败点并求助。未知结果不盲目重放。
- **缺少材料/重要选择**：生成具体问题和推荐选项，绑定 task_id/step_id/version；普通“好的”不能确认不相关旧操作。用户补充只解锁相应任务。
- **权限撤回/登录失效**：暂停相关步骤，说明需要恢复哪项连接或能力。用户授权后重新验证，不能仅因为选择主 Bot 自动扩权。
- **需要外部写入**：复用 pending_actions 的冻结参数、过期检查与一次性领取；新增业务步骤引用及确认结果回接。批准后读取真实结果并安排下一步，拒绝/过期进入等待修改或停止。
- **超时或结果未知**：标 interrupted/unknown，先核实上游结果；上游无幂等键或可查状态时要求用户决定如何继续，不能宣称端到端 exactly-once。
- **额度耗尽**：保存进度并等待明确继续或已授权的预算恢复策略，不自动跨天绕过任务总预算。

具体询问可以是：“周报已整理，缺少本周发布结果。补充版本号，还是先生成缺项草稿？”应带已有结果和下一步，避免只发“任务卡住了”。

确认与任务续跑要兼容现有私聊卡片：无 task 引用的旧 action 继续只执行原操作。确认回接使用唯一 resolution_id；双设备重复批准/回答、已停止任务或旧版本都不能生成第二个步骤。工具定义/参数变化需要新确认，旧批准不能转用于变化后的操作。

## 8. 权限、上下文与有限协作

任务创建时冻结工具与资料范围，执行时再次检查当前权限，取交集。原有定时任务 v1 的只读限制继续保留；新持续任务通过独立策略允许“查询”及“提出需用户批准的操作”，工具执行仍经服务器校验。

后台搜索需要专门接入 web_search/web_read_result、保留轮次查询状态/来源、公开 URL 校验、时间/次数预算及访问验证失败语义；不能只添加工具名。提醒创建/修改、任务管理与记忆写入同样按工具逐项接入，不因为其是内置工具而默认后台可用。

协作首版采用结构化咨询：主 Bot 保留总目标，子 Bot 领取受限步骤，结果返回原任务。只共享必要、获准的任务资料及明确记忆引用；保持当前上下文隔离和敏感信息规则。现有 ask_bot 是本轮嵌套调用，不提供独立持久子任务；新的 Worker 步骤需补独立身份、预算与取消关联。

不解除委派 Bot 的 MCP 禁用规则；需要 MCP 时由有权限的任务负责人执行并将获准结果交给咨询步骤。外部资料被标为不可信后保持现有委派限制；遇到拦截就向用户说明，不能换路径绕过。

建议首个自动推进链最多六次实际 Bot 生成，咨询返回/空回复重试均计数；不允许等待用户时自发生成新问题。任务保存累计调用/费用与主动预算，链上限和总预算在重启后不清零。达到上限保存未完成结果并等待用户显式继续。

完成标准由创建目标及可观察结果判定；模型 completed 只是待校验的候选动作。确认执行、全部必需步骤和必要成果保存均满足后才标完成，不能仅凭“我已经完成”的文字终结任务。

## 9. 运行和通知

复用独立调度进程的部署模式，需常驻后端并监督重启。第一版继续 SQLite、单机明确的 Worker 并发边界，不引入 Redis/Celery 或迁移技术栈。群 v2 当前要求单 API 进程，保持其限制，不因租约存在就宣称多实例取消可靠。

轻量扫描只检查数据库中的到期时间、已授权触发与可执行步骤；空闲不调用模型，不每分钟让模型扫描全部聊天。事件订阅、主动发现新目标后续按来源另设范围与费用预算。

完成、实质变化、失败和需要用户处理时才通知，复用免打扰与去重。求助保留在任务页和原对话，不只依赖限流通知；若通知被抑制，未处理项仍可被回读。

APNs 独立交付：本机可用首版通过刷新收件箱/对话查看；如验收要求锁屏即时求助，APNs、推送权限、开发者账号配置和网络可达后端是交付前置，不把手机本地排程当作任意服务端消息推送。

## 10. 修改范围与难度

**低到中：身份与徽章。** 修改账号存储/API、Swift User/Bot 展示模型、统一头像组件、详情/助理入口及本地缓存。难点是跨设备版本、删除与离线回读，不是画一个徽章。

**中：定时任务 iOS 与明确交办。** 增加 Networking/Core/Data 模型、创建确认、任务列表/历史/控制，保留现有排程幂等和时区规则。自然语言只生成待确认任务草稿，不由模型直接持久修改排程。

**中高：跨会话目标/步骤与有限咨询。** 新增任务存储/API、Worker、事件回读和上下文构造；涉及取消、重启、双设备、版本、预算和既有聊天迁移。可参考群 v2，仍需单独验证私聊与工具场景。

**高：操作确认与自动续跑。** 改造 actions 的任务引用/回接和工具结果检查点，处理结果未知、重复批准和迟到回调。现有卡片 UI 可复用，但完整事务与生命周期不能照搬 UI 代替。

**高且取决于部署：广泛主动发现/跨应用操作。** 新增订阅源、监控范围、推送、账号连接和可执行环境；不纳入推荐首版估算。

建议阶段与粗估（单名熟悉仓库的工程师，含针对性回归；非承诺排期）：

1. P0 身份、选择与徽章：1–2 个工作日。
2. P1 定时任务管理、明确交办入口与运行状态：2–3 个工作日，形成可使用的有限版本。
3. P2 持久步骤、等待补充、有限咨询与中断恢复：4–6 个工作日。
4. P3 MCP 确认回接、完整生命周期回归与交付验收准备：3–5 个工作日。

推荐 B 合计约 **10–16 个工作日**。估算以群 v2 稳定后参考其模式为前提，包含方案涉及的服务端/iOS及本地假服务验证；不包含群 v2 自身修复、APNs、生产部署、真实凭据等待或大规模共享引擎重构。若必须同时做这些项，需重新估算，不能把未验收工作树按可直接复用的完成组件扣减时间。

## 11. 验收与接入顺序

先确认范围，再写正式实施计划。首轮必须覆盖：

1. 主 Bot 设置跨设备、离线回读、更换/删除、旧客户端兼容；置顶/群路由不受改变。
2. 交办与排程幂等、授权草稿确认、时区/错过策略；前轮等用户时不生成重复周期。
3. 离开 App 后继续；重启回读进度；未知模型/操作结果不重放；消息与通知仅去重投递。
4. 连续两次追问、用户补充、双设备竞争、停止/新版本与迟到回答；已完成步骤不重新执行。
5. 咨询回到原任务、权限/记忆隔离、外部资料限制、六次实际调用及任务累计预算。
6. MCP 批准/拒绝/过期/重复确认、工具定义变化、未知执行结果、确认后推进下一步。
7. 实际后端常驻和一个隔离真实任务；区分离线单测、真实模型结果与用户 UI 验收。锁屏求助若列入范围，另验 APNs。

建议接入顺序：群 v2 完成用户验收及主线整合 → 核对迁移/共用边界 → P0/P1 → P2/P3。也可在独立分支先做 P0/P1，但不同时改群 Worker、group_execution_store、群协议和群迁移；每阶段按实际 Git 状态避开并行界面改动。
